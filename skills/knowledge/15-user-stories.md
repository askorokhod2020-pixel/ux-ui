# User stories (пользовательские истории)

User story — короткое описание функции с точки зрения пользователя: кто, что хочет сделать и зачем. Это не техническое задание, а повод для разговора команды. В базе этой темы не было, раздел написан по общепринятой практике Agile (Mike Cohn, Bill Wake).

## 1. Формула
> **Как** [роль], **я хочу** [действие], **чтобы** [ценность / результат].

**Пример:**
> Как постоянный покупатель, я хочу повторить прошлый заказ в один клик, чтобы не собирать корзину заново каждую неделю.

- **Роль** — конкретная: не «пользователь», а «новый посетитель», «администратор салона», «покупатель с ребёнком».
- **Действие** — что человек хочет сделать, без описания интерфейса (не «нажать синюю кнопку»).
- **Ценность** — самая важная часть. Если не можешь сформулировать «чтобы», история не нужна.

## 2. Критерии приёмки
У каждой истории есть критерии: по ним проверяют, что история выполнена. Формат Given / When / Then:

> **Дано** у пользователя есть хотя бы один завершённый заказ,
> **когда** он нажимает «Повторить заказ»,
> **тогда** все товары, которые есть в наличии, добавляются в корзину, а о недоступных показывается сообщение.

Обычно 3–7 критериев: основной сценарий, граничные случаи, ошибки.

## 3. Проверка качества: INVEST
| Буква | Критерий | Вопрос |
|---|---|---|
| **I** — Independent | Независимая | Можно ли сделать её отдельно от других? |
| **N** — Negotiable | Обсуждаемая | Оставляет ли она простор для решения? |
| **V** — Valuable | Ценная | Получает ли пользователь пользу? |
| **E** — Estimable | Оцениваемая | Может ли команда оценить объём? |
| **S** — Small | Небольшая | Влезает ли она в один спринт? |
| **T** — Testable | Проверяемая | Можно ли проверить, что она выполнена? |

## 4. Иерархия
- **Эпик** — большая цель: «Повторные покупки».
- **История** — конкретная функция внутри эпика: «повторить заказ», «сохранить список», «подписка на регулярную доставку».
- **Задача** — техническая работа для разработки истории.

Если история не влезает в спринт, это эпик: дели её по шагам сценария, по типам пользователей, по простому и сложному варианту.

## 5. Правила
1. Пиши от лица реального пользователя, на основе исследования, а не фантазии.
2. Одна история — одна потребность.
3. Не описывай интерфейс в истории. Интерфейс — решение дизайнера.
4. Ценность («чтобы») обязательна.
5. Критерии приёмки пишутся до начала работы.
6. Истории связываются с [работами пользователя (JTBD)](16-jtbd.md): история — это часть решения большой работы.
7. Для дизайнера история — это отправная точка для сценария (user flow): из неё выводятся экраны и состояния.

## 6. Примеры: плохо → хорошо
| Плохо | Почему | Хорошо |
|---|---|---|
| Как пользователь я хочу кнопку «Фильтр» | описан интерфейс, нет ценности | Как покупатель, я хочу сузить каталог по размеру и цене, чтобы быстро найти подходящие варианты |
| Сделать личный кабинет | не история, а задача на всё сразу | Как клиент салона, я хочу видеть свои будущие записи, чтобы не забыть время визита |
| Как пользователь я хочу удобный сайт | непроверяемо | Как новый посетитель, я хочу за 1 минуту понять цены, чтобы решить, подходит ли мне сервис |

```
Эпик: …

1. Дано …, когда …, тогда …
2. …
Связанная работа (JTBD): …
Приоритет (MoSCoW): Must / Should / Could / Won't
Экраны / сценарий: ссылка на Figma
```
